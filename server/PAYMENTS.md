# Robokassa: подготовленный тестовый контур

## Заявка на активацию магазина

Релиз с миграцией `202611150005_publish_storefront.sql` публикует оферту и политику
редакции `2026-11-15.1`. Цены, лимиты, реквизиты и статус публикации берутся из PostgreSQL.
Существующие заказы сохраняют принятую ими версию; оформление с устаревшей версией
будет отклонено до повторного ознакомления. Более новая редакция в БД миграцией не заменяется.

Публичные ссылки (без входа, модалка поверх редактора):

- Тарифы: https://wien.aydar.media/?billing=plans
- Оферта: https://wien.aydar.media/?billing=offer
- Политика: https://wien.aydar.media/?billing=privacy

После релиза проверить `GET /v1/storefront`: `terms.documents_published=true`,
`terms.document_version=2026-11-15.1`, затем открыть ссылки в гостевом браузере.
В кабинете Robokassa заполнить обязательный адрес для корреспонденции, сохранить
анкету и отправить запрос на активацию. Этот адрес не публикуется на сайте.
Контакт поддержки на сайте по решению владельца — только `mail@aydar.media`.
В подробных требованиях Robokassa допускает email, но краткий список требует
также телефон; если модератор запросит его, владелец должен предоставить контакт.
Источник: https://robokassa.com/how-works/.

Активация магазина не включает боевую оплату в Wien. Для приёма настоящих денег
ещё нужны реализация `live`, проверка оплаты через форму Robokassa, настройка
выдачи чеков самозанятого и проверка возврата. Одного заполнения боевых паролей
недостаточно. Не снимать `IsTest=1` вручную в существующей интеграции.

## Режим оплаты

Оплата по умолчанию выключена: `[payments].mode` в `server/config.toml`.
Код поддерживает `disabled` и `test`; `live` намеренно
отклоняется при запуске. Тестовый платёж не списывает деньги, но выдаёт настоящий
месячный лимит внутри Wien **только заранее разрешённому тестовому аккаунту**.
Используйте отдельные аккаунты, а не аккаунты клиентов.

Для разработки и локальных проверок ни подтверждение магазина, ни ключи не нужны.
Для прохождения формы самой Robokassa понадобятся идентификатор магазина и два
**тестовых** пароля из его технических настроек. Реальная форма провайдера пока
не проверена: локальные тесты подменяют её и уведомления.

## Что уже работает

- Один публичный `GET /v1/storefront` возвращает `plans`, `seller`, `terms` и
  `payments.mode` (`disabled` / `test`). Отдельных `/v1/plans` и `/v1/payments/config`
  больше нет. Каталог и условия читаются в одной транзакции с общим снимком БД;
  ответ не кэшируется. Модалка загружает его один раз при открытии. История и
  статусы заказов остаются отдельными запросами с авторизацией.
- Клиент передаёт выбранный тариф и
  увиденные цену, лимит, версию условий. Бэк сверяет их с БД и сам формирует сумму.
- Заказ сохраняет цену в копейках, валюту RUB, лимит, аудиодоступ, название тарифа,
  версию условий и время создания. Ссылка Robokassa возвращается сразу при создании.
  Согласие — только галочка на клиенте, которая включает кнопку оплаты;
  оно не передаётся и не сохраняется на сервере. Поле `accepted` старых клиентов
  принимается для совместимости, но игнорируется.
  Период всегда равен одному месяцу; полные JSON-копии каталога и реквизитов не хранятся.
- Повтор создания с тем же `request_id` возвращает тот же заказ. На аккаунт
  допускается один незавершённый заказ и не более 10 новых заказов за час.
- Подписи SHA-256, разные тестовые пароли для формы и уведомлений, обязательный
  `IsTest=1` в форме и подписанные `Shp_mode=test`, `Shp_order=<UUID>`.
- Только проверенный ResultURL меняет подписку. Сумма сверяется точно, без float;
  повторные уведомления не пополняют баланс. Выдача лимита и запись оплаты
  происходят одной транзакцией. Ошибка оставляет заказ пригодным для повтора.
- Купленные лимит и аудиодоступ сохраняются отдельно от каталога. Правки тарифов
  влияют на новые покупки. При изменении описаний или условий также обновлять
  `storefront.document_version` в БД (в ответе API — `terms.document_version`), чтобы ранее открытое оформление запросило новое
  согласие. Один успешный Assist, включая аудио, расходует один запрос.
- Период начинается при подтверждении и заканчивается в ту же дату/время следующего
  месяца (UTC, с переносом на последний день короткого месяца). Досрочная покупка,
  смена тарифа посреди периода и автоматические списания пока не поддерживаются.
- Модалка содержит оформление и вкладку «Платежи»: последние 20 заказов, повторное
  открытие формы, отмену неоплаченного заказа, автоматическую проверку статуса,
  результат и срок подписки. Возврат из Robokassa открывает ту же модалку.
- Покупка: кнопка «Купить» в карточке создаёт неоплаченный заказ. На заказе —
  итоговая сумма, согласие со ссылками на документы и CTA «Оплатить».
  В web форма Robokassa открывается в той же вкладке; desktop использует браузер.
  Технические названия режима не выводятся покупателю; `IsTest=1` и allowlist
  остаются настройками протокола и не меняются от редактирования интерфейса.
- Web использует HttpOnly cookie и проверку origin; desktop — существующую сессию
  в основном процессе Electron. Ключи Robokassa доступны только серверу.

## Когда появятся данные магазина

1. Создать отдельный аккаунт Wien для проверки. Убедиться, что он принадлежит вам,
   **до** добавления его имени в разрешённый список.
2. В технических настройках Robokassa выбрать **SHA-256** и задать два разных
   тестовых пароля (не боевые). Пароли: 8–256 символов, без двоеточия и управляющих
   символов. Не присылать их в чат и не коммитить.
3. Указать адреса (для другого стенда заменить домен):

   | Поле Robokassa | Метод | Адрес |
   | --- | --- | --- |
   | ResultURL | POST | `https://wien.aydar.media/v1/payments/robokassa/result` |
   | SuccessURL | GET | `https://wien.aydar.media/v1/payments/robokassa/success` |
   | FailURL | GET | `https://wien.aydar.media/v1/payments/robokassa/fail` |

   Для ResultURL нужна доступность извне без входа, captcha или редиректов.
   Аутентификация этого endpoint — подпись уведомления. Success/Fail только
   возвращают в редактор и никогда не являются доказательством оплаты.
   В текущем nginx маршрут `/v1/` уже направляется на backend.
4. Публичные настройки задать в `server/config.toml`:

   ```toml
   [payments]
   mode = "test"
   merchant_login = "wien"
   test_users = ["tester_one", "tester_two"]
   ```

   `test_users` — массив имён аккаунтов **Wien**, не идентификаторов магазинов
   Robokassa. Один пользователь: `["tester_one"]`, несколько — через запятую
   внутри массива. Пустой массив допустим при `mode = "disabled"`, но не в `test`.
   Без секции `[payments]` оплата выключена. Старые переменные
   `WIEN_PAYMENTS_MODE`, `ROBOKASSA_MERCHANT_LOGIN`, `ROBOKASSA_TEST_USERS`
   больше не читаются и не передаются Compose.

   В корневом `.env` оставить только секреты Robokassa (пример — `.env.example`):

   ```dotenv
   ROBOKASSA_TEST_PASSWORD1=<тестовый пароль 1>
   ROBOKASSA_TEST_PASSWORD2=<тестовый пароль 2>
   ROBOKASSA_PASSWORD1=
   ROBOKASSA_PASSWORD2=
   ```

   Последние два поля — placeholders для боевых паролей: текущая интеграция
   их не читает и не использует как замену тестовым паролям.
   На VPS секреты находятся в `/opt/wien/.env`, а TOML поставляется релизом
   как `server.toml` и монтируется в `/app/config.toml`.
   Оба compose-файла передают серверу тестовые пароли из `.env`.
   До заполнения тестовых паролей и списка аккаунтов оставить `mode = "disabled"`.
   Для изменения TOML нужен перезапуск сервера. Неполная конфигурация `test`
   останавливает запуск; секреты не выводятся в ошибках.
5. Обновить сервер и клиент обычным процессом проекта. Миграция
   `202611150004_payment_orders.sql` применяется сервером автоматически.
6. Войти разрешённым аккаунтом, открыть «Тарифы и условия», нажать «Купить» на плане,
   подтвердить условия на созданном заказе и нажать «Оплатить». Проверить успешную
   и неуспешную оплату, закрытие формы, повторное открытие модалки, возврат на сайт,
   появление лимита и срока. Согласно документации Robokassa, тестовые оплаты
   не отображаются в поиске операций кабинета; подтверждение проверять по статусу
   заказа и активации подписки в Wien.

Для выключения новых платежей поставить `mode = "disabled"` в секции `[payments]` TOML и перезапустить
сервер. История остаётся доступна, но ссылки на оплату не выдаются, ResultURL отвечает
503 и подписки больше не активируются. Уже выданный тестовый доступ остаётся до
окончания месяца. Для финального подтверждения незавершённых тестовых заказов
сначала нужно вернуть прежнюю тестовую конфигурацию; не менять пароли/магазин,
пока проверяются незавершённые заказы.

## Необычные ситуации

- Закрытая форма или FailURL оставляет заказ `pending`: можно продолжить оплату.
- «Отменить заказ» прекращает его автоматическую активацию в Wien; это не запрос
  возврата и не отзыв ссылки на стороне Robokassa. Не оплачивать старую ссылку.
- Позднее подтверждение отменённого заказа или подтверждение поверх уже действующей
  подписки записывается как `paid_review`. Уведомление подтверждается провайдеру,
  но доступ не перезаписывается. В интерфейсе предлагается обратиться в поддержку.
- Для проверки состояния использовать номер заказа из интерфейса. В БД доступны
  `invoice_id`, `status`, `paid_at`, `period_ends_at`, купленная цена, лимит и версия условий.
  Для статуса `paid` время подтверждения оплаты совпадает со временем активации.
  Не редактировать статусы вручную для имитации callback: локальные тесты уже
  проверяют подписанный протокол и транзакции.
- Удаление пользователя с заказами не производится каскадно; записи платежей не
  теряются случайно. Автоматического удаления истории пока нет.

## Проверки без ключей

Из корня репозитория, с **отдельной тестовой PostgreSQL**, не рабочей БД:

```sh
DATABASE_URL=postgresql://... cargo test --locked -p wien-server --test payments_db --test subscriptions_db --test accounts_db -- --ignored
cargo test --locked -p wien-server
cargo clippy --locked -p wien-server --all-targets --all-features -- -D warnings
pnpm --dir client test
pnpm --dir client test:payments
pnpm --dir client test:storefront
bash server/scripts/generate-http.sh --check
```

SQLx создаёт отдельные базы для тестов; тестовому пользователю нужен CREATEDB.
Браузерные тесты используют Playwright Chromium (или `PLAYWRIGHT_CHROMIUM_EXECUTABLE`),
локальный mock API и перехват Robokassa. Никаких настоящих платежей они не делают.
CI запускает тесты оплаты вместе с аккаунтами и проверками интерфейса.

## До реальных продаж

Следующий этап — проверка тестового платежа в самом магазине, готовность магазина
к боевым платежам, выбранный механизм чеков самозанятого и возвратов, затем отдельная
поддержка live с боевыми секретами и опубликованными условиями. Простая замена
`IsTest` или тестовых паролей не открывает продажи. Текущая миграция также запрещает
боевые заказы. Автоматические чеки, возвраты и сверка через API провайдера здесь
ещё не реализованы. Реальные деньги не принимаются.
